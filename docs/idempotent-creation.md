# 여행·준비물·경비 생성 재시도

여행 생성, 새 준비물 추가, 경비 추가는 화면의 연속 클릭 방지와 서버의 중복 저장 방지를 함께 사용한다. 버튼을 잠가도 서버가 저장한 뒤 성공 응답만 유실될 수 있다. 같은 논리적 요청을 다시 보낼 때는 처음 발급한 UUID를 재사용한다.

## 요청과 응답

| 작업 | 요청 | 응답 |
| --- | --- | --- |
| 여행 생성 `POST /api/trips` | 기존 `{conditions,items}` + 선택적 `requestId` | 현재 여행 상세. `id`로 같은 여행임을 확인 |
| 준비물 추가 `POST /api/trips/{id}/tasks` | `{content,requestId?}` | 현재 준비물 목록 |
| 경비 추가 `POST /api/trips/{id}/expenses` | `{label,amount,requestId?}` | 현재 경비 목록 |

`requestId`는 하이픈을 포함한 36자리 UUID이며 대문자는 표준 소문자로 정리한다. 생략하면 예전 요청 계약을 유지하며 영수증에 의한 중복 방지는 적용하지 않는다. 같은 키도 다른 회원·다른 작업에서는 독립적이다.

기존 준비물의 `{taskId,done}` 완료 변경은 이번 생성 영수증 범위가 아니다. 여기에 `requestId`를 붙이면 400으로 거절하며, 프런트는 기존 상태 변경 계약을 사용한다.

재시도 응답은 첫 성공 때 보관한 JSON이 아니다. 실제 저장을 반복하지 않고 **현재 상세·목록**을 조회한다. 동행이 이후 추가한 준비물이나 경비도 포함되며 과거 응답으로 최신 화면을 덮어쓰지 않는다. 예약·결제 성공을 뜻하는 응답도 아니다.

## 같은 요청의 판단

- 키 범위는 `(세션 회원 ID, 작업 종류, requestId)`다. 작업은 `TRIP_CREATE`, `TASK_ADD`, `EXPENSE_ADD`다.
- 여행 지문은 저장하는 여행 조건과 날짜·방문 순서·장소 ID·시작 시각이다. 숙소 메모 null은 실제 저장과 같이 빈 문자열로 정리한다. 배열이 달라도 같은 날짜/방문 순서이면 같은 의미로 정렬한다. 서버가 무시하는 임시 일정 ID·예약 상태·장소 이름/좌표/요금은 지문에 포함하지 않는다.
- 준비물 지문은 여행 ID와 앞뒤 공백을 정리한 내용이다. 경비는 여행 ID와 앞뒤 공백을 정리한 이름·원 단위 정수 금액이다.
- 객체 키를 재귀적으로 정렬한 JSON으로 SHA-256을 계산한다. JVM마다 `Map.of` 순회 순서가 달라져도 같은 입력은 같은 해시다.
- 같은 키에 다른 실효 내용을 보내면 409다. 요청 ID를 바꾸면 새로운 생성 의도로 처리하므로 실패할 때마다 새 UUID를 만들면 안 된다.

## 저장 순서와 현재 권한

UUID가 있는 요청은 **활동 회원 행 → 기존 여행 행** 순서로 잠근다. 초대와 공개 일정 가져오기도 같은 순서를 사용한다. 같은 회원의 재시도가 겹치면 첫 트랜잭션 종료를 기다린 뒤 성공 영수증을 다시 조회한다.

새 요청은 검증한 실제 데이터와 성공 영수증을 같은 트랜잭션에 저장한다. 실패하면 둘 다 롤백하며 실패한 키를 소비하지 않는다. 여행 재시도는 영수증을 먼저 확인하므로 첫 저장이 끝난 뒤 장소 공급자에 장애가 생겨도 후보를 다시 조회하지 않는다.

영수증이 있어도 현재 참여 권한과 실제 대상 존재를 확인한다. 참여가 끝났으면 403이며 초대 수락이나 소유권을 복구하지 않는다. 여행을 삭제하면 영수증의 여행 FK는 NULL이 되지만 키와 대상 UUID는 남는다. 준비물·경비가 없어졌거나 여행이 삭제된 성공 요청은 409로 안내하고 재생성하지 않는다. 새로 만들 의도라면 새 요청 키를 발급해야 한다.

키 없는 예전 요청은 기존 저장 경로를 유지한다. 준비물 추가와 경비 추가는 영수증이 있어도 여행의 공동 편집 버전을 임의로 올리지 않는다. 기존 버전 정책과 응답 모양은 유지한다.

## 보관 정보와 삭제

V21의 `trip_mutations`는 회원 ID·작업·요청 UUID·입력 해시·여행 ID·대상 UUID·최초 생성 시각만 보관한다. 원문 출발지·준비물 문구·경비 이름/금액과 전체 응답은 이 표에 복제하지 않는다. 해시도 회원의 비공개 행동 기록이므로 공개 API로 반환하지 않는다.

계정이 유지되는 동안 삭제된 대상의 영수증도 유지하여 오래된 재시도가 데이터를 되살리지 못하게 한다. 탈퇴 시 해당 회원의 영수증을 제거한다. 다른 동행의 영수증과 공동 준비물·경비는 기존 보존 정책을 따른다. 공통/H2와 Oracle 마이그레이션의 컬럼·키·NULL 의미·한국어 코멘트는 동일하다.

## 검증 기준

`IdempotencyFlowTest`는 실제 HTTP·세션·CSRF·DB에서 다음을 검사한다. 테스트 결과는 [검증 기록](verification.md)에 별도로 기록한다.

- 같은 요청의 순차·동시 재시도와 회원/작업별 키 분리, 다른 본문·다른 여행의 키 재사용 409.
- 여행·준비물·경비 각각 6개 동시 요청에서 실제 데이터 1건, 성공 영수증 1건.
- 첫 성공 후 장소 공급자가 준비되지 않은 상태에서도 기존 여행 반환, 최신 목록과 서버가 무시하는 메타데이터 처리.
- 실제 영수증 INSERT 직후 실패를 주입한 뒤 여행·기본 준비물·영수증의 트랜잭션 롤백과 같은 키 재사용 성공.
- 대상 삭제·여행 삭제의 409와 재생성 0건, 소유권 이전 후 참여 해제의 403과 접근 복구 방지.
- 탈퇴 회원의 영수증 제거와 타 회원 영수증·공동 준비물·경비 보존, 기존 키 생략 요청 호환.

서버의 DB 영수증은 브라우저를 닫아도 남지만, 브라우저가 원래 UUID·입력 스냅샷을 잃으면 새 요청과 이전 재시도를 자동 구분할 수 없다. 개인 입력을 localStorage에 보관하지 않으며 화면이 보장하는 재시도 수명은 아래 프런트 계약과 구분한다.

## 프런트 재시도 수명과 복구

- 여행 생성은 회원·추천 결과 세대·선택 코스별로 UUID를 보관한다. 같은 추천 결과의 같은 코스를 다시 저장하면 같은 UUID를 사용한다. 다른 코스는 별도 요청이며 새 추천 결과를 받으면 이전 결과의 키를 정리한다.
- 준비물과 경비는 회원·여행·추가 작업을 구분한다. 준비물 `content.trim()`, 경비 `label.trim()`과 숫자 금액이 같은 재시도는 같은 UUID를 사용하며, 내용을 바꾸어 전송하면 새 UUID를 사용한다. 기존 준비물의 완료 상태 변경에는 추가용 키를 붙이지 않는다.
- UUID와 본문 비교값은 화면의 메모리에만 둔다. 회원·여행·화면 수명이 끝나면 제거하며 localStorage나 sessionStorage에 개인 문구·지출 내용을 저장하지 않는다. 새로고침·페이지 종료를 넘어 같은 키를 복원하는 기능은 없으므로, 응답이 불확실하면 화면을 닫기 전에 같은 버튼으로 결과를 확인하거나 내 여행/기록 목록을 먼저 확인한다.
- 서버 성공 응답을 받으면 같은 작업 범위와 UUID에 해당하는 키만 정리한다. 전송 당시 원본 초안과 현재 입력이 같은 경우에만 입력을 비우며, 늦은 응답이 새 초안을 지우지 않는다. 성공 뒤 사용자가 같은 내용을 다시 입력하는 것은 의도적인 새 추가이므로 새 UUID를 발급한다.
- 저장 성공과 후속 목록 조회 실패를 구분한다. 성공 응답을 받은 입력은 먼저 정리하고 이후 조회 오류를 표시하며, 조회 실패 때문에 저장 요청을 자동 재전송하지 않는다. 불확실한 응답에는 내용을 유지하고 ‘결과 확인’ 안내를 제공한다.
- 현재 회원과 실제 주소가 바뀌면 이전 응답이 새 화면의 초안·캐시·이동을 바꾸지 않도록 기존 계정/경로 검사를 유지한다. 서버의 기대 회원 헤더 검사도 함께 적용하며 재시도 키를 인증이나 객체 접근 권한의 대체 수단으로 사용하지 않는다.
