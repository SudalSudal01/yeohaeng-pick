# 검증 기록

2026-10-12, Windows 로컬 개발 환경에서 확인했습니다. 구현 상태와 실제 공급자 검증을 구분합니다.

## 자동 검증 결과

| 검증 | 결과 | 확인한 범위 |
| --- | --- | --- |
| `backend/mvnw.cmd -q test` | 33개 통과 | 실제 HTTP 16개 + 일정 엔진 7개 + 예약 시간 엔진 4개 + 경로 변환 4개 + 장소 분류 2개 |
| `frontend/npm test` | 2개 통과 | 로그아웃 및 403 응답 후 CSRF 토큰 재조회 |
| `frontend/npm run build` | 통과 | TypeScript 검사와 Vite 배포용 빌드 |
| `frontend/npm run format:check` | 통과 | 프론트와 Java 소스의 일관된 포맷 |

서버 통합 테스트는 임의 포트와 별도의 H2 메모리 DB를 사용합니다. 테스트에서 실제 메일·AI·예약을 요청하지 않습니다.

- 비로그인 접근, CSRF 누락, 다른 사람의 일정 읽기/변경, 일반 회원의 관리자 접근을 거절합니다.
- 초대 수락 전 접근, 중복 수락, 동행의 오래된 버전으로 저장하는 상황을 검증합니다.
- 예약으로 고정한 장소 교체와 이전 버전 적용을 거절하고, 정상 변경/방문일정 복원을 확인합니다.
- 공개 공유 링크의 길이·정보 제외·폐기를 검증합니다. 출발지·숙소·개인 경비·예약 기록을 공개하지 않습니다.
- 메시지 요청 수락 전 추가 발송, 외부인의 대화 접근, 차단 이후 발송을 거절합니다.
- 비밀번호 재설정 토큰의 일회성 소비와 기존 세션의 무효화를 확인합니다.
- 숙소 후보/비용 저장, 외부 예약 실패 사유의 저장, 잘못된 중첩 입력의 400 응답을 확인합니다.
- 여러 지역의 방문 배정, 장소 중복 방지, 기간/지역 제약, 도보와 차량의 추정 이동 차이를 확인합니다.
- 같은 분류의 비용이 모두 같은 실제 검색 조건에서 서로 다른 방문 구성을 제공하는지, 후보가 하나뿐이면 중복 안내와 함께 그 장소만 사용하는지 확인합니다.
- 선택 단계의 거리 반영, 시간 제한으로 제외한 장소를 다음 방문 시간에 더하지 않는 처리를 검증합니다.
- 병원·주차장·컨벤션센터 제외, 업종 코드 없는 공원 분류, 주소에 따른 지역 검증을 확인합니다.
- 경로의 초/분·좌표 순서·분리된 선, 미제공 요금과 0원, 택시 요금의 오용 방지, 결과 없음과 잘못된 응답을 검증합니다. 여행 외부인의 경로/출발지 조회와 임의 항목을 거절하고 조회 전후 일정 버전이 유지되는지 확인합니다.

Codex 브라우저에서 화면을 직접 조작했습니다. 화면 캡처는 `docs/screenshots`에 있습니다.

1. 이메일 가입/로그인 → 여행 만들기의 지역·날짜·예산·취향·숙소 선택 → 세 코스 비교 → 저장을 확인했습니다.
2. 2026-11-07~11-08의 1박 2일 여행을 저장하고 서버 재시작 후 동일한 여행을 다시 열었습니다.
3. 날짜 입력이 DOM에만 표시되고 React 상태에 반영되지 않는 경우를 발견해 `onInput`도 처리했습니다. 요약과 저장된 기간이 일치하는지 다시 확인했습니다.
4. 모바일 390×844에서 홈·여행 상세·비교 대화상자를 확인했습니다. `scrollWidth`와 `clientWidth`가 모두 375px로, 가로 넘침이 없었습니다. 대화상자는 내부 세로 스크롤로 모든 내용을 볼 수 있습니다.
5. 동대문디자인플라자를 국립중앙박물관으로 바꾸는 비교에서 인원 전체 활동비 -20,000원, 추정 이동 +17분, 이후 방문 시간 변경을 확인했습니다. 적용 후 실제 일정과 활동비 162,000원 → 142,000원이 갱신됐습니다.
6. 숙소 예시 비용을 포함한 합계 422,000원 → 402,000원과 예산 초과 122,000원 → 102,000원 안내를 확인했습니다. 실제 교통비·객실 수는 별도 확인 항목으로 표시합니다.
7. 실행 스크립트가 기존 8080/8081을 사용하지 않고 18081/5173을 사용하는지 확인했습니다. Oracle Java 실행기의 자식 JVM 문제를 수정해 실제 JVM PID를 보존합니다.
8. 커뮤니티에서 로컬 시연임을 명시한 의견 게시물을 등록하고 댓글을 저장했습니다. 실제 여행 후기·평점이나 동행 모집을 꾸며 넣지 않았습니다.
9. 마이페이지의 대화 수신 안내와 저장 버튼 사이에 24px 간격을 적용하고 데스크톱과 모바일에서 확인했습니다. 모바일 가로 넘침도 없었습니다.
10. 마이페이지의 취향 6개를 데스크톱에서는 같은 너비의 한 줄로, 모바일에서는 3개씩 두 줄로 표시했습니다. 390px·320px에서 페이지와 각 버튼의 가로 넘침이 없었고 기존 선택 상태도 유지됐습니다.

## 지도·AI 연결 준비와 실제 응답 확인

키가 비어 있는 상태에서 [Kakao·Gemini 연결 안내](maps-ai-setup.md)를 추가했습니다. 공식 모델 안내의 신규 프로젝트 Gemini 2.5 접근 제한을 반영해 기본 모델을 `gemini-3.5-flash-lite`로 변경했습니다.

`scripts/Test-Integrations.ps1`의 기본 점검은 외부 요청 없이 세 키의 설정 유무만 확인합니다. `-Live`만 지정한 요청은 무료 등급 확인 안내로 거절되는 것도 확인했습니다. 실요청 점검은 무료 등급을 확인한 후 실행하며, 지도 SDK 표시와 실제 여행 추천의 검증을 대체하지 않습니다.

연결 준비 단계에서는 백엔드 테스트 13개, 프론트 테스트 2개·빌드·포맷 검사가 통과했습니다. 당시 Windows에서 실행 중인 JAR 잠금으로 원래 경로의 재패키징이 실패해, `.tools`의 별도 폴더에 `pom.xml`과 `src`만 복사한 뒤 테스트 재실행 없이 `-DskipTests package`로 실행 JAR 생성을 확인했습니다. 그 단계에서는 개발 서버와 로그인 세션을 유지했습니다.

이후 사용자가 로컬 `.env`에 키를 입력했습니다. Gemini의 테스트 후보 ID에 대한 구조화 JSON 응답을 확인했습니다. Kakao의 첫 요청은 앱의 지도·장소 API 비활성화로 403이었고, 개발자 콘솔의 제품 설정 → 카카오맵에서 ON 상태와 해당 앱의 일간 무료 쿼터 제공 안내를 확인한 후 재요청이 성공했습니다. 계정 키와 콘솔 화면의 개인 정보는 문서에 포함하지 않습니다.

설정을 반영하기 위해 여행픽 서버를 종료·재빌드·시작했습니다. 공개 설정에서 지도·AI 설정 활성화, 예시 데이터 모드 비활성화를 확인했습니다. 앱 서버를 거친 서울숲 검색에서도 실제 `KAKAO` 출처와 좌표가 반환됐고, 탐색 화면에서 장소 상세·리뷰 링크가 표시됐습니다.

로그인한 브라우저의 여행 상세에서 지도 영역이 비어 있는 것을 발견했습니다. JavaScript 키의 SDK 도메인에 현재 개발 주소가 등록되지 않은 것이 원인이었습니다. 플랫폼 키 → JavaScript 키 설정에서 `http://127.0.0.1:5173`을 저장한 후 실제 지도 타일·마커·방문 순서 연결선을 확인했습니다. 다른 도메인이나 OAuth 설정, 결제 설정은 변경하지 않았습니다. 지도 연결선은 직선 좌표 기반으로, 실제 도로·대중교통 경로를 조회한 결과가 아닙니다.

별도 검증 탭에서 서울 당일치기·2명·맛집/카페/전시 조건으로 추천을 요청했습니다. 세 카드 모두 `AI 취향 평가 반영 · 조회된 장소`를 표시해 실제 앱의 Gemini 경로가 실행된 것을 확인했습니다. 저장된 여행에는 추천 엔진 이름을 보관하지 않으므로 기존 여행의 존재만으로 AI 연결을 검증하지 않았습니다.

실제 응답에서는 첫 두 코스가 같은 장소로 구성되는 문제도 발견했습니다. 검색 API의 동일 분류 비용이 같은 추정치인 조건에서는 가격 가중치만으로 차이가 생기지 않았습니다. 이전 코스와 같은 날의 구성이 겹칠 때 조회된 같은 분류의 대안 중 점수 차이가 가장 작은 장소로 교체하도록 보완했습니다. 후보나 시간 제약으로 최종 구성이 여전히 겹치면 양쪽 코스에 안내를 넣습니다. 확인하지 않은 유료 전시를 단정하던 부제도 수정했습니다. 회귀 테스트 2개를 추가한 뒤 서버 15개·프론트 2개 테스트와 빌드·포맷 검사를 통과했습니다. 이번에는 개발 서버를 종료한 뒤 원래 경로에서 실행 JAR 재패키징에 성공하고 다시 시작했습니다.

재로그인 후 같은 검증 조건으로 다시 생성했습니다. 세 카드 모두 실제 AI 평가 반영 표시를 유지했고, 첫 두 코스는 전시 후보가 달랐으며 세 번째는 방문지 하나를 추가해 서로 다른 장소 집합을 표시했습니다. 확인되지 않은 유료 전시 문구도 사라졌습니다. 390×844 모바일에서는 세 카드가 세로로 배치됐고 `clientWidth`와 `scrollWidth`가 모두 375px로 가로 넘침이 없었습니다. 검증용 추천은 별도 여행으로 저장하지 않았고, 캡처는 Git에서 제외한 `.tools`에만 보관했습니다.

## Gmail SMTP 연결 확인

2026-10-12 로컬 환경에서 Gmail SMTP(587, STARTTLS) 인증과 테스트 메일 발송을 확인했고, 사용자가 실제 수신을 확인했습니다. 비공개 `.env`에만 자격 증명을 보관하고 메일 발송을 활성화한 뒤 개발 서버를 다시 시작했습니다.

실제 로그인한 계정의 마이페이지에서 `인증 메일 받기`를 눌렀고, Spring 메일 발송 경로를 거쳐 `인증 메일을 보냈어요.` 안내가 표시됐습니다. 사용자가 받은 메일의 링크에서 인증을 완료한 뒤 마이페이지를 새로고침했고, `이메일 인증 완료` 표시와 재발송 버튼이 사라진 것을 확인했습니다. 실제 발송 → 수신 → 링크 인증 → 계정 반영까지 확인했습니다.

실제 계정의 비밀번호 재설정은 아직 확인하지 않았습니다. 자동 테스트에서 검증한 토큰 일회성·세션 무효화와 실제 메일 흐름을 구분합니다.

실사용자 정보가 포함된 화면 캡처와 발송 연결 점검 기록은 Git에 포함하지 않는 로컬 `.tools` 폴더에만 보관합니다. 계정 정보·앱 비밀번호·인증 토큰도 커밋하지 않습니다.

## 장소 분류·거리 반영·실제 교통 연결

2026-10-12에 카카오 공식 문서의 최신 대중교통·도보 REST API와 카카오모빌리티 자동차 API를 확인하고 기존 REST 키로 공개 장소 사이의 성공 응답을 받았습니다. 새 키/유료 설정은 추가하지 않았습니다. 서버의 저장 일정·숙소·회원별 출발지 검색 토큰을 해석하는 전용 엔드포인트를 추가했습니다.

로그인한 실제 앱의 여행에서 대중교통 경로 3개(55/56/59분, 각각 1,750원), 도보 1개(256분), 자동차 2개(27/30분, 통행료 0원)가 반환됐습니다. 이후 공개 출발지 검색과 저장 숙소를 출발점으로 조회해 시간·요금·경로가 바뀌는 것을 확인했습니다. 공급자 조회 시각·출처·공식 길찾기 링크가 표시되고, 지도는 조회한 도로/단계별 실선을 표시했습니다. 경로를 여러 번 바꿀 때 지도 인스턴스가 쌓이던 문제를 수정해 지도는 유지하고 기존 마커/선을 해제하도록 바꿨습니다. 조회 작업에서 여행/예약 상태를 수정하지 않았습니다.

390×844와 320×740 모바일에서 각각 `clientWidth/scrollWidth`가 375/375, 305/305로 가로 넘침이 없었습니다. 출발·도착·수단 버튼·조회 결과·지도 이동을 확인했고 화면 크기는 원상 복구했습니다. 지도와 입력 폼 캡처는 실사용 여행 정보가 포함되어 `.tools`에만 저장합니다.

공개 장소 이름/좌표를 포함하는 AI 후보 평가와 거리 가중치를 적용한 세 코스도 실제 앱에서 새로 요청해 모두 `AI 취향 평가 반영 · 조회된 장소`로 표시됐습니다. 세 코스의 방문 집합이 달랐고 균형 코스는 도심 주변 후보를 연결했습니다. 추천 일정의 시간은 여전히 휴리스틱 추정이며 구간 조회 결과와 별도입니다. 검증용 코스는 저장하지 않았습니다.

실제 데이터 점검에서 업종 코드가 없는 `여행 > 공원`을 추가로 허용했고, 대중교통 응답에 도보 단계가 없을 때 0분으로 단정하지 않도록 `null`로 바꿨습니다. 회귀 테스트를 반영해 서버 24개 테스트와 프론트 2개·빌드·포맷을 통과했습니다. 마지막 보완을 적용하려고 실행 JAR을 재빌드·재시작했으며 세션은 종료되고 로컬 여행 DB는 유지됩니다.

## 교통 예약 시간 연결 검증 (2026-10-12)

서버 33개 테스트가 통과했습니다. 순수 예약 시간 엔진 4개와 실제 HTTP 흐름 16개를 포함합니다. 경계에서 정확히 끝나는 방문, 자정을 넘는 이동, 교통편끼리의 여유 시간 충돌, 취소/미연결 제외, 앞당기기·늦추기의 비용/체류/고정 방문 보존, 하루 범위 밖 실패를 검증했습니다. HTTP에서는 도착/여유 입력 검증, 출발 시간만 보내던 이전 형식 호환, 비교의 비변경성, 적용/이력, 현재 예약을 침범하는 장소 변경·복원 거절, 동행 권한/오래된 버전/CSRF/공개 공유 제외를 확인했습니다.

확장한 HTTP 시나리오가 같은 루프백 IP의 인증 요청 한도를 함께 소모하는 문제는 각 테스트 전 테스트 서버의 제한 기록만 초기화해 분리했습니다. 실제 필터는 유지하며 한 시나리오의 31번째 로그인 요청이 429/Retry-After를 반환하는 회귀 검증도 추가했습니다. 운영 제한은 변경하지 않았습니다.

브라우저 검증은 별도 18082 메모리 DB와 localhost:5174의 예시 여행에서 진행했습니다. 실사용자 여행이나 외부 예매를 변경하지 않았고 Kakao/Gemini/메일 키 없이 확인했습니다. 가상 열차 10:30~11:30, 출발 전/도착 후 각각 30분 입력으로 10:00 방문과의 충돌을 만들었습니다. 앞당기기는 10:00→08:30 한 곳, 늦추기는 네 방문 각각 +120분을 제시했습니다. 늦추기를 저장하면 첫 방문 12:00과 나머지 변경 시각이 반영되고 겹침 없음으로 바뀌었으며 활동비 108,000원과 교통 예약 시간은 유지됐습니다.

390×844 화면의 본문 375/375px, 조정 창 328/328px, 320×740 화면의 본문 305/305px, 조정 창 258/258px로 가로 넘침이 없었습니다. 도착 날짜 입력의 브라우저 input 이벤트가 상태에 반영되지 않는 문제를 발견해 출발 입력과 동일하게 onInput/onChange를 처리한 뒤 실제 저장을 재검증했습니다. 검증 스크린샷은 개인정보가 없는 별도 예시이며 `.tools/booking-schedule-*.jpg`로 로컬에만 보관합니다.

검증 후 테스트 서버를 종료하고 실행 중인 여행픽을 한 번 재시작했습니다. 기존 로컬 DB에 V3→V4 한 건의 마이그레이션이 성공했고 기본 포트 5173/18081 기동을 확인했습니다. 세션은 종료되어 다시 로그인이 필요합니다. 비교 시각 표시 함수는 컴포넌트와 분리해 개발 중 Fast Refresh가 불필요하게 무효화되지 않도록 정리했고 최종 프론트 빌드·포맷 검사도 통과했습니다.

실제 여행일 운행·좌석·지연, 역까지 이동 시간 자동 수집, 장소 영업시간 검증과 모든 조합의 최적화는 검증 범위에 포함하지 않습니다. PostgreSQL 운영 마이그레이션은 별도 검증이 필요합니다.

## 확인하지 않은 영역

- Kakao/Gemini의 한도 소진·공급자 장애·다중 요청 시 동작, 장기간 사용량과 과금 내역. 앱 무료 쿼터 안내와 실제 연결만 확인
