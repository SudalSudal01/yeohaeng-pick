# 메시지 사용 흐름과 개인정보 경계

## 상대를 찾고 요청하기

메시지 화면의 **새 대화**에서 닉네임 앞부분을 두 글자 이상 입력하고 검색 결과에서 회원을 직접 선택합니다. 같은 닉네임은 공개 회원 식별 표시로 구분합니다. 검색은 최대 20명과 더 있는지 여부만 반환하며 이메일·가입일·개인 취향은 반환하지 않습니다. 상대가 모든 새 대화를 껐거나 현재 동행만 허용했는데 함께하는 여행이 없으면 결과에서 제외합니다. 본인·탈퇴 회원·양방향 차단 관계도 제외합니다.

커뮤니티 작성자의 대화 링크로 들어와도 서버에서 상대를 다시 확인합니다. URL의 `name`은 표시 이름이나 권한의 근거로 사용하지 않습니다. 요청을 보낼 때는 회원 ID를 전달하고 서버가 현재 수신 설정과 차단·동행 관계를 다시 검사합니다. 이메일을 넣은 예전 요청은 이메일을 조회하지 않고 400으로 거절합니다.

처음 요청하면 첫 인사 한 건이 저장되고 받은 요청/보낸 요청에서 수락 대기를 확인합니다. 수신자만 수락·거절할 수 있고, 수락 전에는 추가 메시지를 보낼 수 없습니다. 이미 두 회원의 대화가 있으면 새 방을 만들거나 인사를 임의로 전송하지 않고 기존 방을 반환합니다. 화면은 이 경우를 안내하고 입력한 인사를 해당 방 초안으로 보존합니다. 기존 초안이 있으면 덮어쓰지 않고 별도로 보관합니다.

## 화면과 긴 대화

모바일은 대화 목록과 대화방을 한 화면씩 보여 주고 뒤로 버튼으로 돌아갑니다. 데스크톱은 목록과 대화를 나란히 보여 줍니다. 기록을 독립 스크롤하며 전송 가능한 방의 입력줄·전송 버튼을 화면 안에 유지합니다. 긴 닉네임·여행 제목은 헤더 안에서 끝까지 읽을 수 있습니다. 수락 대기·차단·종료 상태는 입력폼 대신 읽기 전용 안내를 표시하며, 낮은 화면에서는 중복 안내를 줄여 수락 버튼과 기록 공간을 확보합니다. 실제 남은 화면 높이를 계산하고 `visualViewport` 변화에 맞춰 키보드·주소창이 차지하는 공간을 반영합니다.

기본 조회는 최신 50개를 시간순으로 제공합니다. 이전 대화 보기로 더 불러오며 `created_at`, `id` 순서를 함께 사용해 같은 시각의 기록도 빠뜨리지 않습니다. 앞에 기록을 추가할 때 읽던 위치를 유지합니다. 새 메시지를 읽고 있다면 최신 위치로 이동하지만 이전 대화를 읽는 중에는 새 메시지 버튼으로 안내합니다. 폴링 사이에 50개보다 많은 기록이 쌓여 중간 연결이 끊겼다면 누락을 조용히 합치지 않고 추가 조회 또는 최신 위치 확인을 안내합니다.

초안은 대화방별 메모리에 보관하며 localStorage에 개인 문구를 저장하지 않습니다. 이전 방의 늦은 전송 응답은 다른 방의 초안을 지우지 않습니다. 페이지를 닫거나 로그인 세션이 끝나면 초안은 유지되지 않습니다.

## 전송·차단·권한

- 모든 메시지 API는 로그인, 변경 요청은 CSRF 토큰이 필요합니다.
- 개인 대화는 양 당사자만 조회합니다. 단체 대화는 현재 여행 참여자만 조회·전송할 수 있습니다. 여행에서 나가거나 해제되면 예전 메시지 접근도 끝납니다.
- 개인 대화의 요청·수락·전송·차단은 두 회원 행을 ID 순서로 잠가 처리합니다. 반대 방향 동시 요청은 한 방으로 합쳐지고, 차단과 전송이 겹치면 같은 잠금 경계에서 선후 관계를 정합니다. 단체 대화는 별도의 여행 행 잠금을 사용합니다.
- 차단 후 기존 기록은 읽을 수 있지만 새 메시지와 요청은 주고받지 않습니다. 차단은 여행 참여 관계를 자동 변경하지 않습니다.
- 재시도에는 첫 전송 때 만든 `requestId` UUID를 다시 사용합니다. 같은 ID·방·작성자·본문일 때만 이미 저장한 메시지의 응답을 반환합니다. 본문·작성자·방을 바꾸어 키를 재사용하면 409입니다. 전송 상태와 접근 권한은 재시도에도 검사합니다.
- 공백만으로는 메시지를 보낼 수 없으며 전체 길이는 1~2,000자입니다. 화면 제한뿐 아니라 서버에서도 검사합니다. 본문을 HTML로 실행하지 않습니다.
- 검색·상대 확인은 회원별 분당 60회, 새 요청 12회, 전송 90회, 차단 변경 30회로 제한합니다. 메모리 항목 만료와 최대 크기를 관리합니다. 단일 서버 기준이며 다중 서버 운영 전에는 공유 저장소로 옮겨야 합니다.
- 신고는 해당 메시지 한 건과 당시 공개 닉네임만 보존합니다. 개인 대화 전체를 관리자에게 공개하지 않습니다.

## API 계약

| 경로 | 내용 |
| --- | --- |
| `GET /api/messages/recipients?query=닉네임` | `{items:[{id,nickname}],hasMore}`. 2~30자 앞부분 검색. `%`, `_`, `!`는 SQL 와일드카드가 아닌 문자로 처리 |
| `GET /api/messages/recipients/{memberId}` | 요청 가능한 상대의 `{id,nickname}`. 없거나 연락할 수 없으면 같은 404 안내 |
| `POST /api/messages` | `{recipientId,body}`. 대화 상세와 `requestCreated` 반환. 기존 이메일 요청은 400 |
| `GET /api/messages` | 내 개인 대화와 현재 참여 여행의 단체방. 단체방은 실제 `tripTitle` 제공 |
| `GET /api/messages/{id}?before={messageId}` | 최신/이전 50개와 `hasOlder`, `olderCursor`, `canSend`, `blocked`. 커서는 해당 방의 메시지 ID여야 함 |
| `POST /api/messages/{id}` | `{body,requestId?}`. 새 화면은 UUID를 전달하고 같은 전송 재시도에만 재사용 |
| `POST /api/messages/{id}/respond` | `{accept}`. 수신자의 대기 요청만 처리하며 수락할 때 차단·탈퇴를 재검사 |
| `PUT /api/messages/blocks/{memberId}` | `{enabled}`. 본인의 양방향 전송 경계에 반영 |

`blocked`는 양방향 차단 관계의 유무이며 누가 차단했는지는 반환하지 않습니다. 메시지 ID와 커서는 개인정보가 없는 임의 식별자입니다. 과거 메시지 ID·신고 연결은 보존합니다. V19는 기록 조회 인덱스, V20은 클라이언트 재시도 UUID도 사용하는 ID 의미를 설명하는 코멘트 변경이며 기존 데이터 값을 변경하지 않습니다.

## 검증 범위와 한계

회원 검색·이메일 조회 차단·수신 설정·양방향 차단·수락 주체·제3자 접근·동시 요청·차단/전송 경합·350개 동일 시각 기록의 전체 페이지 회수·재전송 키 재사용을 실제 HTTP로 검사합니다. 모바일은 320·390px와 낮은 창 높이, 키보드로 줄어든 visualViewport 모사를 포함합니다. 실기기별 소프트 키보드와 네트워크 환경은 별도 점검이 필요합니다.

현재는 주기적 조회 기반이며 WebSocket·분산 세션·푸시 알림·파일 첨부까지 구현한 것으로 표시하지 않습니다. 탈퇴의 전역 보호와 요청 제한은 단일 JVM 기준입니다. 실제 가격·좌석·결제 상태와 관계없이 대화 전송 성공은 메시지 저장 성공만 의미합니다.
