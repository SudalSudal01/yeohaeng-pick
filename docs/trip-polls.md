# 여행 공동 의사결정 투표

여행 상세의 **함께 결정하는 투표**에서 현재 참여자가 식당, 방문 장소, 출발 시각처럼 함께 정할 질문을 올립니다. 한 후보만 고르는 투표와 여러 후보를 고르는 투표를 지원하며, 결과만으로 일정·예약·숙소·경비를 자동 변경하지 않습니다. 동행이 결과를 확인한 뒤 기존 비교·예약 기능에서 필요한 변경을 직접 적용합니다.

## 사용자 흐름

1. 현재 여행 참여자가 질문, 선택 방식, 2~10개 후보와 선택적인 마감 시각을 입력합니다.
2. 참여자는 후보를 고르고 저장합니다. 다시 저장하면 이전 선택 전체를 바꾸며 아무 후보도 보내지 않으면 본인의 투표를 취소합니다.
3. 화면은 진행 중 투표를 먼저 보여 주고, 종료된 투표는 별도 영역에 보존합니다. 15초 재조회 중에도 저장하지 않은 선택 초안은 서버의 내 선택이 실제로 바뀌지 않는 한 유지합니다.
4. 투표를 만든 현재 참여자 또는 현재 여행 소유자가 직접 마감하거나 삭제할 수 있습니다. 마감 시각을 정했다면 한국 현지 시각이 지난 뒤 자동 종료 상태로 보입니다.

새 질문과 결과에는 외부 공급자의 가격·영업·재고·예약 확인 의미가 없습니다. 새 투표 생성과 사용자의 직접 마감은 행동한 본인을 제외한 현재 동행에게 [앱 안 알림](notifications.md)을 만듭니다. 자동 기한 종료 알림, 질문/후보 수정, 재개, 익명 투표, 결과로 일정 자동 적용은 현재 범위에 포함하지 않습니다.

## 생성 규칙

`POST /api/trips/{tripId}/polls`

```json
{
  "title": "둘째 날 저녁은 어디에서 먹을까요?",
  "selectionType": "MULTIPLE",
  "options": [
    { "label": "전통시장" },
    { "label": "해변 식당" },
    { "label": "숙소 근처" }
  ],
  "closesAt": "2026-10-14T18:00:00"
}
```

| 입력 | 계약 |
| --- | --- |
| `title` | 공백 제외 1~120자 |
| `selectionType` | `SINGLE` 또는 `MULTIPLE` |
| `options` | 2~10개. 각 `label`은 공백 제외 1~100자이며 대소문자를 무시해 중복 불가 |
| `closesAt` | 선택. 현재보다 뒤인 한국 현지 `LocalDateTime`, 연도 9999 이하. `null`이면 자동 마감 없음 |
| 여행당 투표 수 | 삭제되지 않은 질문 최대 50개. 같은 여행 행 잠금 안에서 검사 |

성공은 생성한 투표 객체를 반환합니다. 제목과 후보 앞뒤 공백은 서버가 제거합니다. 후보 ID와 정렬 순서는 서버가 만들며 생성 뒤 질문·후보·순서를 수정하는 API는 없습니다.

## 조회와 응답 개인정보

`GET /api/trips/{tripId}/polls`는 현재 참여자에게만 최대 50개를 최근 생성 순으로 반환합니다. 생성·투표·마감 응답도 같은 객체 형식입니다.

```json
{
  "id": "b1902091-36a9-4bd4-8e54-442697c05e81",
  "title": "둘째 날 저녁은 어디에서 먹을까요?",
  "selectionType": "MULTIPLE",
  "status": "OPEN",
  "closesAt": "2026-10-14T18:00:00",
  "closedAt": null,
  "version": 0,
  "createdAt": "2026-10-13T12:30:00",
  "creatorName": "수달수달",
  "canManage": true,
  "votedMemberCount": 2,
  "eligibleMemberCount": 3,
  "options": [
    {
      "id": "후보 UUID",
      "label": "전통시장",
      "sortOrder": 0,
      "voteCount": 2,
      "selectedByMe": true
    }
  ]
}
```

- `votedMemberCount`: 한 개 이상 후보를 고른 현재 참여자의 중복 없는 수
- `eligibleMemberCount`: 현재 `trip_members`에 있는 참여자 수
- `voteCount`: 해당 후보를 고른 현재 참여자 수
- `selectedByMe`: 요청한 로그인 회원이 고른 후보인지 여부
- `canManage`: 요청 회원이 질문 생성자이거나 현재 여행 소유자인지 여부

복수 선택에서는 한 사람이 여러 후보에 표를 주므로 후보별 `voteCount` 합계가 `votedMemberCount`나 `eligibleMemberCount`보다 클 수 있습니다. API는 후보별 합계와 요청 회원의 선택만 제공합니다. 다른 회원별 선택, 회원 내부 UUID, 이메일, 표를 저장한 시각은 응답하지 않습니다. 공개 일정 링크와 공개 일정 가져오기에도 투표를 포함하지 않습니다.

## 투표·취소·재투표

`PUT /api/trips/{tripId}/polls/{pollId}/ballot`

```json
{ "optionIds": ["후보 UUID 1", "후보 UUID 2"] }
```

서버는 URL의 여행과 투표 소속, 현재 참여, OPEN 상태, 후보 소속을 다시 확인합니다. `SINGLE`은 후보를 최대 한 개, `MULTIPLE`은 최대 10개 받을 수 있습니다. 같은 ID를 반복하거나 다른 투표의 후보를 섞으면 기존 선택을 지우기 전에 400으로 거절합니다.

유효한 요청은 기존 선택을 전부 지우고 새 후보를 저장합니다. 빈 `optionIds`는 본인의 투표 취소입니다. 투표 뒤 반환된 집계는 현재 참여자의 표만 포함합니다. 마감 시각 경계에서는 후보 검증 직후 동일한 KST 기준으로 다시 OPEN 여부를 검사하므로 종료 뒤 표가 추가되지 않습니다.

## 상태·마감·삭제

| API 상태 | 의미 |
| --- | --- |
| `OPEN` | 저장 상태가 OPEN이고 `closesAt`이 없거나 아직 미래여서 투표 가능 |
| `CLOSED` | 관리자가 직접 마감. `closedAt`에 KST 마감 시각 저장 |
| `EXPIRED` | DB 저장 상태는 OPEN이지만 `closesAt`이 현재 KST와 같거나 과거인 자동 종료 |

`POST /api/trips/{tripId}/polls/{pollId}/close`는 `{ "version": 0 }`을 받고 성공 시 version이 1 증가한 최신 객체를 반환합니다. `DELETE /api/trips/{tripId}/polls/{pollId}`도 같은 본문으로 현재 version을 검사하고 성공 시 204를 반환합니다. 둘 다 질문을 만든 현재 참여자 또는 현재 여행 소유자만 실행할 수 있습니다. 이미 직접/자동 종료된 투표를 다시 마감할 수 없고, 마감 취소나 재개 API는 없습니다. 종료된 투표도 관리자는 삭제할 수 있습니다.

투표 version은 마감·삭제 충돌에만 사용합니다. 개별 회원의 표가 바뀌어도 증가하지 않으며 여행의 일정 version도 바꾸지 않습니다. 화면은 마감/삭제 확인을 연 시점의 version과 최신 재조회 값을 비교해 달라졌다면 최신 결과를 확인하게 합니다.

## 권한과 오류

| 상황 | HTTP |
| --- | --- |
| 형식·길이·후보 수·중복 후보·지난 마감·후보 소속 오류 | 400 |
| 로그인하지 않음 | 401 |
| 현재 여행 비참여, CSRF 실패, 마감/삭제 관리 권한 없음 | 403 |
| 여행 또는 그 여행의 투표를 찾을 수 없음 | 404 |
| 이미 종료, 오래된 version, 여행당 50개 상한 | 409 |

클라이언트가 회원 ID, 작성자 ID, 집계 수, 투표 상태를 입력하지 않습니다. 서버가 세션 회원과 DB의 현재 여행/후보 관계로 계산합니다. 기존 투표 요청은 여행 ID와 투표 ID를 함께 제한한 잠금 조회로 소속을 먼저 확인하고, 그 뒤 후보와 본인 표 SQL을 검증된 투표 ID 안에서 실행해 다른 여행의 ID를 URL에 섞는 접근을 막습니다.

## 동시 요청과 잠금 순서

투표 생성은 `TripService.access`로 여행 행을 잠근 채 상한을 확인합니다. 기존 투표의 쓰기는 여행 행을 먼저 잠그고 해당 투표 행을 잠급니다. 참여 종료·소유권·다른 여행 쓰기와 같은 첫 잠금 순서를 사용합니다.

- 동시 생성은 여행 행 안에서 현재 개수를 세므로 50개를 넘지 않습니다.
- 서로 다른 회원의 표와 같은 회원의 재투표는 순서대로 처리됩니다. 같은 회원은 마지막으로 성공한 전체 선택만 남습니다.
- 투표와 마감이 겹치면 잠금을 먼저 얻은 작업 뒤에 상태를 다시 확인합니다. 마감 완료 뒤 표가 남지 않습니다.
- 참여 종료와 투표가 겹치면 투표가 먼저 완료돼도 이어지는 참여 종료가 그 회원의 표를 삭제합니다. 참여 종료가 먼저면 이후 요청은 403입니다.
- 탈퇴는 `AccountLifecycle` 경계 안에서 관련 여행을 ID 순서로 잠그고 표를 삭제한 뒤 참여를 끊습니다. 진행 중인 표 저장이 탈퇴 뒤 되살아나지 않게 합니다.
- 목록은 여행 행을 잠근 한 트랜잭션에서 질문·후보·표·현재 참여 인원을 읽어 한 응답에 서로 다른 시점의 집계를 섞지 않습니다.

이 잠금 계약은 현재 단일 앱 인스턴스의 DB 트랜잭션을 기준으로 표적 검증했습니다. 다중 서버 운영 전에는 회원 탈퇴의 JVM 잠금을 분산 경계로 바꾸고 실제 Oracle 부하/교착을 별도로 검증해야 합니다.

## 나가기·탈퇴·삭제 보존 범위

| 사건 | 처리 |
| --- | --- |
| 동행 나가기·소유자의 참여 해제 | 대상 회원의 해당 여행 표만 삭제. 질문·후보·다른 표 보존 |
| 새 초대 수락 | 이전에 삭제한 표를 복원하지 않음. 새로 선택해야 함 |
| 질문 생성자가 여행에서 나감 | 질문 보존. 현재 여행 소유자가 관리 가능 |
| 질문 생성자가 회원 탈퇴 | 본인 표 삭제, 질문 보존. 비식별 회원 행과 조인해 `탈퇴한 회원`으로 표시 |
| 투표 삭제 | 해당 후보와 표를 FK cascade로 함께 삭제. 일정·예약·경비·여행 version 유지 |
| 여행 삭제 | 그 여행의 질문·후보·표를 FK cascade로 함께 삭제 |

투표 생성·수동 마감 알림도 질문과 같은 트랜잭션에서 저장합니다. 참여 종료 시 그 회원이 해당 여행에서 받은 알림을 지우며, 투표나 여행을 삭제하면 관련 알림도 FK cascade로 제거합니다. 새로 참여한 회원에게 과거 알림을 소급하지 않습니다.

공동 질문의 제목과 후보는 사용자가 입력한 자유 텍스트입니다. 나가기와 탈퇴 때 작성한 질문을 자동 삭제하지 않으므로 이메일·전화번호 같은 개인정보를 적지 않도록 화면에서 안내해야 합니다. 운영 전에는 자유 입력 개인정보 삭제 요청과 보존 기간 정책을 확정해야 합니다.

## DB 구조와 시간 기준

V16의 공통 H2/PostgreSQL 이력과 Oracle 19c 전용 이력은 같은 3개 테이블·18개 컬럼을 만듭니다. V17은 적용한 V16을 수정하지 않고 `(poll_id,option_id)` 외래키 순서의 인덱스를 추가해 후보·투표 삭제 시 자식 표 탐색 범위와 Oracle 잠금 대기를 줄입니다.

| 테이블 | 역할과 주요 제약 |
| --- | --- |
| `trip_polls` | 여행·작성자 FK, 질문 120자, `SINGLE|MULTIPLE`, 저장 상태 `OPEN|CLOSED`, 선택 마감/수동 마감 시각, 별도 version |
| `trip_poll_options` | 투표 안 후보 ID·100자 라벨·0~9 표시 순서. `(poll_id,id)`와 `(poll_id,sort_order)`로 소속/중복 제한 |
| `trip_poll_votes` | `(poll_id,member_id,option_id)`별 선택. 후보 복합 FK로 다른 투표 후보 참조 차단 |

모든 테이블·컬럼에는 역할, 상태 값, NULL 의미, 시각 기준, 개별 선택 비공개와 삭제 범위를 설명하는 한국어 DB COMMENT가 있습니다. V15의 22개 테이블·181개 컬럼에 V16의 3개·18개가 더해졌고, 실제 Oracle에서 25개 테이블·199개 컬럼과 코멘트 누락 0건을 확인했습니다. 적용·백업 근거는 [Oracle 연결 문서](oracle-setup.md)에 기록합니다.

`closesAt`, 자동 종료 판정, 직접 `closedAt`은 `Asia/Seoul` 기준의 오프셋 없는 시각입니다. 애플리케이션이 만든 KST 현재 시각을 투표 가능/마감 SQL에 바인딩하므로 Oracle/H2 세션의 `CURRENT_TIMESTAMP` 차이에 기대지 않습니다. `createdAt`은 DB 현지 시각이며 오프셋을 저장하지 않으므로 운영 DB/JVM 시간대를 KST로 맞추고 배포 검증에서 확인해야 합니다.

## 현재 검증 범위

2026-10-13 기준 V18을 포함한 기본 H2 전체 195개, Oracle QA의 `TripPollFlowTest` 12개·`NotificationFlowTest` 9개와 전체 195개, 프론트 전체 48개, 프로덕션 빌드·번들 예산·포맷 검사가 통과했습니다. HTTP 검사는 세션·CSRF·초대, 입력·50개 한도, 내부 회원 ID 비노출, 재투표/취소, 수동/자동 마감, 생성·수동 마감 알림, 동시 요청, 나가기/참여 해제/탈퇴, cascade를 포함합니다.

브라우저에서 생성, 중복 후보 검증과 포커스 이동, 표 저장·변경·취소, 직접 마감을 확인했고 콘솔 오류는 0건입니다. 320px·390px 모두 가로 넘침 0, 입력 16px, 버튼 44px 이상, 후보 행 71px 이상이었습니다. 연속 30자 닉네임도 카드 안에서 줄바꿈하며 마감 입력·표시는 브라우저 시간대와 무관하게 한국 시간으로 처리합니다. 초기 JavaScript는 알림 센터 포함 328.39kB, gzip 105.04kB입니다. 실제 Oracle V16~V18 적용·백업·인덱스·코멘트와 최신 세부 결과는 [검증 기록](verification.md)에서 관리합니다.
